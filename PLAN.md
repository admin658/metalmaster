1) Goal (1 sentence) To audit the Metal Master monorepo for correctness, architecture, performance, and developer experience, and provide a prioritized list of actionable recommendations.  2) Quick repo map assumptions *   The repository is a TypeScript monorepo using Yarn 3.x workspaces, with packages located in `packages/`. *   The primary applications are a Next.js web app (`packages/web`) and an Expo mobile app (`packages/mobile`). *   Shared code is organized into `packages/shared`, `packages/shared-types`, etc. *   The backend is Supabase, with keys and URLs managed via environment variables. *   The web application is deployed on Netlify, which also runs serverless functions from the `netlify/functions` directory. *   Git submodules (`alphatab`, `vexflow`) are used for including large, external projects. *   The project uses ESLint for linting, Prettier for formatting, Jest for testing, and has Git hooks managed by Husky.  3) Findings *   **Correctness**     *   **Positive**: The root `tsconfig.json` has `"strict": true` enabled, which is a best practice for type safety.     *   **Negative**: The benefits of strict mode are undermined by the widespread use of `// @ts-ignore` and explicit `: any` types. The search results confirm these are prevalent.     *   **Negative**: The ESLint rule `@typescript-eslint/no-explicit-any` is turned off in `.eslintrc.json`, encouraging the use of `any` and reducing type safety across the repo.  *   **Architecture**     *   **Positive**: The monorepo is well-structured with Yarn workspaces, separating concerns into `web`, `mobile`, and `shared` packages.     *   **Concern**: Environment variables appear to be accessed directly (e.g., `process.env.SUPABASE_URL`) within the Next.js frontend source code. Variables must be prefixed with `NEXT_PUBLIC_` to be exposed to the browser, and non-prefixed variables can be `undefined` on the client-side or even leak server secrets.     *   **Concern**: The `tsconfig.json` path aliases (`@/*`) might be too broad and could lead to confusing imports. A more explicit structure like `@/web/*` or `@/shared/*` is typically more maintainable.     *   **Complexity**: The presence of large git submodules (`alphatab`, `vexflow`) adds significant complexity to the build process, dependency management, and general developer onboarding.  *   **Performance**     *   **Positive**: The Netlify configuration uses `esbuild` for bundling serverless functions, which is very fast.     *   **Opportunity**: The size of the Next.js and Expo bundles is unknown. Given the complexity, an analysis is warranted to identify potential optimizations for faster load times.  *   **DX (Developer Experience)**     *   **Positive**: A comprehensive set of scripts in the root `package.json` for development, building, and testing simplifies common tasks.     *   **Positive**: Use of Husky for git hooks and a config for Conventional Commits (`cz`) helps maintain code quality and commit hygiene.     *   **Negative**: Allowing `any` and `@ts-ignore` degrades the developer experience by creating a false sense of security and making refactoring more difficult and error-prone.     *   **Opportunity**: While a root `jest.config.cjs` exists, it's unclear how well testing is enforced or adopted within each package.  *   **Security**     *   **Risk**: Improper handling of environment variables in the Next.js app could potentially expose server-side secrets if `process.env` is accessed in a way that leaks to the client bundle.     *   **Risk**: Without a recent dependency audit, there may be vulnerable packages in the lockfile.  4) Top 10 prioritized recommendations 1.  **Correct Environment Variable Usage:** In `packages/web`, ensure any environment variables needed on the client-side are prefixed with `NEXT_PUBLIC_`. Audit all usages of `process.env` in `packages/web/src` to prevent leakage of server-side secrets. 2.  **Re-enable `no-explicit-any` Lint Rule:** In `.eslintrc.json`, change the `@typescript-eslint/no-explicit-any` rule from `"off"` to `"warn"`. This will highlight all existing `any` usages without breaking the build, allowing for incremental refactoring. 3.  **Establish a "No New `@ts-ignore`" Policy:** Begin a campaign to refactor away existing `// @ts-ignore` comments, starting with the most critical application logic. Use `// @ts-expect-error` with a descriptive comment for cases that are truly necessary. 4.  **Run a Dependency Audit:** Execute `yarn npm audit` to identify and patch known vulnerabilities in project dependencies. 5.  **Gradually Refactor `any` Types:** Incrementally replace `any` types with more specific types, `unknown`, or generics. Start in shared packages to maximize impact. 6.  **Establish a Clear Testing Strategy:** Define and document a testing strategy for each package type (`web`, `mobile`, `shared`). Ensure Jest is configured to run tests located within each package, not just the root `tests` directory. 7.  **Analyze Bundle Sizes:** Use `next-bundle-analyzer` for the web app and a similar tool for Expo to inspect bundle composition and identify large dependencies that could be optimized. 8.  **Clarify Path Alias Strategy:** Refine the `tsconfig.json` `"paths"` to be more explicit (e.g., `"@/shared/*": ["./packages/shared/src/*"]`) to improve import clarity and prevent incorrect module resolution. 9.  **Document Submodule Handling:** Create a short guide in `README.md` or `docs/` explaining why the `alphatab` and `vexflow` submodules exist, and how to initialize and update them. 10. **Add Package-Level Scripts:** While root scripts are good, add `lint`, `test`, and `build` scripts to the `package.json` of each individual package (`web`, `mobile`, etc.) to allow for more granular quality checks and builds.  5) “Fast wins” (< 1 hour) *   **Fix Env Vars:** Audit `packages/web/src` for `process.env` and prefix client-side variables with `NEXT_PUBLIC_`. *   **Enable `any` lint rule:** Change the rule to `"warn"` in `.eslintrc.json`. *   **Run security audit:** Run `yarn npm audit` and address critical vulnerabilities. *   **Add package scripts:** Add common scripts to individual `package.json` files that delegate to the root runner if needed.  6) “Bigger bets” (1-3 days) *   **Eliminate `any` and `@ts-ignore`:** A full pass to fix all warnings from the newly enabled lint rule and remove all `@ts-ignore` comments. This will significantly improve the long-term health of the codebase. *   **Build out Test Suite:** Implement comprehensive unit and integration tests for a critical user flow in both the web and mobile apps, establishing a pattern for future tests. *   **Analyze and Optimize Bundles:** Install and configure bundle analyzers, investigate the largest modules, and implement optimizations like code-splitting or dependency replacement.  7) Verification checklist (Windows-friendly commands) *   `yarn lint`: To check for linting errors, including the newly enabled `no-explicit-any` warnings. *   `yarn test`: To ensure all existing tests still pass after any refactoring. *   `yarn build:web`: To confirm the Next.js application still builds successfully without errors. *   `yarn build:mobile`: To confirm the Expo app still builds successfully.
